# LearnHouse Internationalization (i18n) Implementation

This document explains how internationalization is implemented in LearnHouse, covering the architecture, patterns, and tools used.

## Overview

LearnHouse uses **session/cookie-based i18n** with `next-intl` for the Next.js frontend. This approach provides clean URLs without language prefixes (e.g., `/courses` instead of `/en/courses`) while maintaining user language preferences across sessions.

### Supported Languages

- 🇬🇧 **English** (en) - Default
- 🇫🇷 **Français** (fr)
- 🇪🇸 **Español** (es)
- 🇩🇪 **Deutsch** (de)
- 🇧🇬 **Български** (bg)

## Architecture

### Translation Files Structure

```
apps/web/messages/
├── en.json    # English (source)
├── fr.json    # French
├── es.json    # Spanish
├── de.json    # German
└── bg.json    # Bulgarian
```

Each translation file contains namespaced keys organized by component or feature:

```json
{
  "common": {
    "save": "Save",
    "cancel": "Cancel",
    "delete": "Delete"
  },
  "courses": {
    "title": "Courses",
    "noCoursesYet": "No courses yet",
    "createCourseToAddContent": "Create courses to add content"
  },
  "activityModals": {
    "assignment": {
      "title": "Assignment Title",
      "create": "Create Assignment"
    }
  }
}
```

### Locale Detection Flow

```
User visits page
       ↓
1. Check authenticated user's preferred_locale (from session)
2. Check NEXT_LOCALE cookie (for guests)
3. Check Accept-Language header (browser default)
4. Fallback to 'en'
       ↓
Load translation file (messages/{locale}.json)
       ↓
Render UI in selected language
```

### Language Switching

**For authenticated users:**
- Preference saved to database (`preferred_locale` field)
- Persists across devices and sessions

**For guest users:**
- Preference saved to `NEXT_LOCALE` cookie
- Persists on same browser

## Implementation Patterns

### Basic Component Translation

```tsx
'use client';
import { useTranslations } from 'next-intl';

export default function CourseList() {
  const t = useTranslations('courses');
  const c = useTranslations('common');
  
  return (
    <>
      <h1>{t('title')}</h1>
      <p>{t('noCoursesYet')}</p>
      <button>{c('create')}</button>
    </>
  );
}
```

### Server Component Translation

```tsx
import { getTranslations } from 'next-intl/server';

export default async function CoursePage() {
  const t = await getTranslations('courses');
  
  return <h1>{t('title')}</h1>;
}
```

### Translation with Variables

```tsx
// Translation file
{
  "welcome": "Welcome, {name}!",
  "studentsCount": "{count, plural, =0 {No students} =1 {1 student} other {# students}}"
}

// Component
t('welcome', { name: user.name })
t('studentsCount', { count: 42 })  // "42 students"
```

### Rich Text Formatting

```tsx
// Translation file
{
  "terms": "I agree to the <link>terms and conditions</link>"
}

// Component
t.rich('terms', {
  link: (chunks) => <Link href="/terms">{chunks}</Link>
})
```

## Best Practices

### 1. Namespace by Component

Each component should have its own namespace to prevent key conflicts:

```tsx
// ✅ Good
const t = useTranslations('UserEditGeneral');
t('title')  // Clear which component this belongs to

// ❌ Bad
const t = useTranslations('app');
t('title')  // Which title? Ambiguous
```

### 2. Use Descriptive Keys

```tsx
// ✅ Good - Self-documenting
t('emailLabel')
t('saveButton')
t('deleteConfirmation')

// ❌ Bad - Not clear
t('label1')
t('btn')
t('text')
```

### 3. Group Related Translations

```json
{
  "UserEditGeneral": {
    "labels": {
      "email": "Email",
      "username": "Username"
    },
    "buttons": {
      "save": "Save Changes",
      "cancel": "Cancel"
    },
    "messages": {
      "saveSuccess": "Profile updated successfully"
    }
  }
}
```

### 4. Use Common Namespace for Shared Text

```tsx
const c = useTranslations('common');

<button>{c('save')}</button>    // Reused across app
<button>{c('cancel')}</button>
<button>{c('delete')}</button>
```

## Translation Management

### Utility Scripts

Located in `apps/web/utils/`:

**`sync_translations.py`** - Syncs all language files to match `en.json` structure:
```bash
python utils/sync_translations.py
```
- Adds missing keys from English to other languages
- Removes extra keys not in English
- Maintains same key order as English
- Preserves existing translations

**`check_translations.py`** - Validates translation files:
```bash
python utils/check_translations.py
```
- Reports unused keys in `en.json`
- Identifies potentially missing keys
- Compares language files for completeness
- Lists untranslated strings (same as English)

### Workflow

1. **Add new keys** to `en.json`
2. **Run sync script** to propagate to all languages
3. **Translate** the new keys in each language file
4. **Run check script** to verify completeness

## Key Implementation Details

### Root Layout Integration

The root layout detects locale and provides translations to all components:

```tsx
// apps/web/app/layout.tsx
import { NextIntlClientProvider } from 'next-intl';

export default function RootLayout({ children }) {
  const locale = detectLocale(); // From session/cookie
  const messages = await import(`../messages/${locale}.json`);
  
  return (
    <html lang={locale}>
      <body>
        <NextIntlClientProvider locale={locale} messages={messages}>
          {children}
        </NextIntlClientProvider>
      </body>
    </html>
  );
}
```

### Language Selector Component

Located at `apps/web/components/Objects/LanguageSelector/LanguageSelector.tsx`:

```tsx
const changeLocale = async (newLocale: string) => {
  if (session?.user) {
    // Save to database for authenticated users
    await updateUserPreference({ preferred_locale: newLocale });
  } else {
    // Save to cookie for guests
    setCookie('NEXT_LOCALE', newLocale);
  }
  router.refresh(); // Reload with new locale
};
```
