# LearnHouse i18n Implementation Strategy

## Executive Summary

This document outlines the complete internationalization (i18n) strategy for LearnHouse, covering both the Next.js frontend and FastAPI backend.

**🎯 Key Approach: Session/Cookie-Based (No URL Changes)**

Instead of URL-based routing (`/en/courses`, `/fr/courses`), LearnHouse uses:
- **Cookie storage** for guest users (`NEXT_LOCALE` cookie)
- **Database preference** for authenticated users (`preferred_locale` field)
- **Same URLs for all languages** - simpler, cleaner, easier to implement

| Aspect | Session-Based ✅ (Chosen) | URL-Based ❌ (Alternative) |
|--------|---------------------------|----------------------------|
| URLs | `/courses` (clean) | `/en/courses`, `/fr/courses` |
| Routing refactor | Not needed | Must refactor entire app directory |
| User preference | Persists in DB/cookie | Can be lost |
| API URLs | Unchanged `/api/v1/...` | Unchanged |
| SEO | Moderate | Better (but less relevant for SaaS) |
| Implementation | Simpler | More complex |

## Session-Based i18n Approach (No URL Changes)

**Key Decision:** LearnHouse will use **session/cookie-based locale selection** instead of URL-based routing (`/en/`, `/fr/`).

### Why Session-Based?

1. **Cleaner URLs:** `/courses` instead of `/en/courses`
2. **No routing refactor:** Existing routes stay exactly the same
3. **Better UX for SaaS:** User preference persists across sessions
4. **Simpler implementation:** No need to refactor entire app directory
5. **API URLs unchanged:** Backend endpoints remain at `/api/v1/...`

## Recommended Libraries

### Frontend: **next-intl** (with session/cookie configuration)
**Rationale:**
- Official Next.js App Router support with server components
- **Supports both URL-based AND session-based i18n** (we're using session-based)
- Type-safe translations with TypeScript
- Server-side rendering compatible
- Smaller bundle size than react-i18next
- Built specifically for Next.js 13+ App Directory
- Works seamlessly with both client and server components
- [Official docs for session-based approach](https://next-intl-docs.vercel.app/docs/routing/without-i18n-routing)

**Alternative considered:** react-i18next (rejected - primarily client-side, larger bundle, less Next.js App Router integration)

### Backend: **Babel** (GNU gettext) + **polib**
**Rationale:**
- Industry-standard i18n for Python
- Simple, lightweight, and proven
- Works seamlessly with FastAPI
- Easy integration with translation management tools
- Compatible with existing Pydantic models
- No heavy dependencies

**Alternative considered:** python-i18n (rejected due to less mature ecosystem)

## Implementation Details

### Frontend Implementation

#### 1. Locale Storage Strategy (Session-Based, No URL Changes)

**Cookie + Session Approach:**
- Locale stored in `NEXT_LOCALE` cookie for guest users
- Locale stored in database `preferred_locale` field for authenticated users
- No URL changes required
- Simple locale switcher updates cookie/preference

**Advantages:**
- ✅ Cleaner URLs (no `/en/`, `/fr/` prefixes)
- ✅ Simpler routing structure
- ✅ No need to refactor existing routes
- ✅ Better for SaaS/authenticated applications
- ✅ Locale persists across sessions

**Trade-offs:**
- ❌ Less SEO-friendly (but LearnHouse is behind authentication mostly)
- ❌ Can't share language-specific URLs easily

#### 2. Locale Detection Priority (Session-Based)

1. **Authenticated users:** Database `preferred_locale` field (from session)
2. **Guest users:** `NEXT_LOCALE` cookie
3. **First visit:** `Accept-Language` header
4. **Organization default:** Organization's `default_locale`
5. **Fallback:** `en`

#### 3. Translation File Structure

**Format:** JSON for next-intl

#### 4. Implementation Code Examples

**Root Layout Setup (apps/web/app/layout.tsx):**
```tsx
'use client'
import { NextIntlClientProvider } from 'next-intl';
import { useEffect, useState } from 'react';
import { useLHSession } from '@components/Contexts/LHSessionContext';

export default function RootLayout({ children }: { children: React.ReactNode }) {
  const session = useLHSession() as any;
  const [messages, setMessages] = useState(null);
  const [locale, setLocale] = useState('en');

  useEffect(() => {
    // Detect locale from session or cookie
    const detectedLocale = detectLocale(session);
    setLocale(detectedLocale);

    // Load translation messages
    import(`../messages/${detectedLocale}.json`).then(setMessages);
  }, [session]);

  if (!messages) return null;

  const isRTL = ['ar', 'he', 'fa'].includes(locale);

  return (
    <html lang={locale} dir={isRTL ? 'rtl' : 'ltr'}>
      <body>
        <NextIntlClientProvider locale={locale} messages={messages}>
          {children}
        </NextIntlClientProvider>
      </body>
    </html>
  );
}

function detectLocale(session: any): string {
  // 1. Authenticated user preference
  if (session?.user?.preferred_locale) {
    return session.user.preferred_locale;
  }

  // 2. Cookie
  const cookieLocale = document.cookie
    .split('; ')
    .find(row => row.startsWith('NEXT_LOCALE='))
    ?.split('=')[1];
  if (cookieLocale) return cookieLocale;

  // 3. Browser default
  if (typeof navigator !== 'undefined') {
    const browserLang = navigator.language.split('-')[0];
    if (['en', 'fr', 'es', 'ar'].includes(browserLang)) {
      return browserLang;
    }
  }

  // 4. Fallback
  return 'en';
}
```

**Locale Detection Utility (apps/web/i18n/request.ts):**
```tsx
import { cookies } from 'next/headers';

export async function getLocale(session: any): Promise<string> {
  // Server-side locale detection

  // 1. User preference from session
  if (session?.user?.preferred_locale) {
    return session.user.preferred_locale;
  }

  // 2. Cookie
  const cookieStore = cookies();
  const localeCookie = cookieStore.get('NEXT_LOCALE');
  if (localeCookie?.value) {
    return localeCookie.value;
  }

  // 3. Fallback
  return 'en';
}
```

**Locale Switcher Component:**
```tsx
'use client';
import { useRouter } from 'next/navigation';
import { useLHSession } from '@components/Contexts/LHSessionContext';
import { setCookie } from '@services/utils/cookies';
import { updateUserPreference } from '@services/users';

export function LocaleSwitcher() {
  const router = useRouter();
  const session = useLHSession() as any;
  const currentLocale = session?.user?.preferred_locale || 'en';

  const changeLocale = async (newLocale: string) => {
    if (session?.user) {
      // Authenticated: save to database
      await updateUserPreference({ preferred_locale: newLocale });
    } else {
      // Guest: save to cookie
      setCookie('NEXT_LOCALE', newLocale, { maxAge: 31536000 }); // 1 year
    }

    // Reload to apply new locale
    router.refresh();
  };

  return (
    <select value={currentLocale} onChange={(e) => changeLocale(e.target.value)}>
      <option value="en">English</option>
      <option value="fr">Français</option>
      <option value="es">Español</option>
      <option value="ar">العربية</option>
    </select>
  );
}
```

#### 5. API Request Interceptor (Send Locale to Backend)

**Create utility to add X-Locale header (apps/web/services/utils/api.ts):**
```typescript
import { getSession } from 'next-auth/react';

function getLocaleFromCookie(): string {
  if (typeof document === 'undefined') return 'en';

  const cookie = document.cookie
    .split('; ')
    .find(row => row.startsWith('NEXT_LOCALE='));

  return cookie ? cookie.split('=')[1] : 'en';
}

export async function fetchWithLocale(url: string, options: RequestInit = {}) {
  const session = await getSession();
  const locale = session?.user?.preferred_locale || getLocaleFromCookie();

  const headers = {
    ...options.headers,
    'X-Locale': locale,
  };

  return fetch(url, { ...options, headers });
}
```

#### 6. Dynamic Content Translation

For user-generated content (courses, descriptions):
- Store translations in `translations` JSON field
- Fetch based on current locale from request
- Fallback to default language if translation missing

**Backend content translation helper:**
```python
# apps/api/src/i18n/content_translator.py
from typing import Optional, Any

def get_translated_field(
    obj: Any,
    field: str,
    locale: str,
    fallback_locale: str = 'en'
) -> str:
    """
    Get translated value for a field from object's translations JSON.

    Args:
        obj: Database object with translations field
        field: Field name to translate (e.g., 'name', 'description')
        locale: Target locale
        fallback_locale: Fallback if translation missing

    Returns:
        Translated string or original value
    """
    # Return original field if locale is default
    if locale == fallback_locale:
        return getattr(obj, field, '')

    # Check if translations exist
    if not obj.translations:
        return getattr(obj, field, '')

    # Get translation for locale
    locale_translations = obj.translations.get(locale, {})
    if field in locale_translations:
        return locale_translations[field]

    # Fallback to original
    return getattr(obj, field, '')

# Usage in endpoint:
@router.get("/courses/{course_id}")
async def get_course(
    course_id: int,
    request: Request,
    current_user: dict = Depends(get_current_user),
    db: Session = Depends(get_session)
):
    locale = detect_locale(request, current_user)
    course = db.get(Course, course_id)

    # Translate course fields
    return {
        "id": course.id,
        "name": get_translated_field(course, "name", locale),
        "description": get_translated_field(course, "description", locale),
        # ... other fields
    }
```

### Backend Implementation

#### 1. Translation Utility

```python
# apps/api/src/i18n/translator.py
import gettext
from functools import lru_cache
from pathlib import Path

LOCALE_DIR = Path(__file__).parent.parent.parent / 'locales'

@lru_cache(maxsize=None)
def get_translator(locale: str = 'en'):
    """Get translator instance for given locale."""
    try:
        return gettext.translation(
            'messages',
            localedir=LOCALE_DIR,
            languages=[locale],
            fallback=True
        )
    except FileNotFoundError:
        # Fallback to English
        return gettext.translation(
            'messages',
            localedir=LOCALE_DIR,
            languages=['en'],
            fallback=True
        )

def _(message: str, locale: str = 'en') -> str:
    """Translate a message."""
    translator = get_translator(locale)
    return translator.gettext(message)
```

#### 2. Locale Detection Middleware (Updated for Session-Based)

```python
# apps/api/src/i18n/locale_detector.py
from fastapi import Request
from typing import Optional

def detect_locale(request: Request, user: Optional[dict] = None) -> str:
    """
    Detect user locale from request.

    Priority (Session-based approach):
    1. User's database preference (if authenticated)
    2. X-Locale header (sent from frontend cookie)
    3. Accept-Language header
    4. Fallback to 'en'
    """

    # 1. User preference from database (highest priority)
    if user and user.get('preferred_locale'):
        return user['preferred_locale']

    # 2. Check X-Locale header (sent from frontend via cookie)
    if locale := request.headers.get('X-Locale'):
        return locale

    # 3. Check Accept-Language header (browser default)
    accept_lang = request.headers.get('Accept-Language', '')
    if accept_lang:
        # Parse: "en-US,en;q=0.9,fr;q=0.8"
        locale = accept_lang.split(',')[0].split('-')[0]
        if locale in ['en', 'fr', 'es', 'ar', 'de', 'pt', 'zh', 'ja']:
            return locale

    # 4. Fallback
    return 'en'
```

```python
async def update_course_translation(
    course_id: int,
    locale: str,
    translation: dict,
    db: Session = Depends(get_session)
):
    """Update course translation for specific locale."""
    course = db.get(Course, course_id)
    if not course:
        raise HTTPException(404, "Course not found")

    course.translations = course.translations or {}
    course.translations[locale] = translation
```

1. Install and configure next-intl (session-based mode)
2. Add `preferred_locale` field to User model (database migration)
3. Create translation file templates (`messages/en.json`)
4. Set up backend translation utilities (gettext + locale_detector)
5. Update root `layout.tsx` with NextIntlClientProvider

### Phase 2: Core UI Translation (Week 2-3)
1. Extract all hardcoded strings from auth pages to `messages/en.json`
2. Extract navigation and common UI strings
3. Translate dashboard components
4. Implement locale switcher component (updates cookie/DB)
5. Create `fetchWithLocale()` utility for API calls with `X-Locale` header

### Phase 3: Content Translation (Week 4-5)
1. Implement course translation endpoints (PUT/GET `/translations/{locale}`)
2. Build translation UI for course creators
3. Add organization locale settings (default_locale, supported_locales)
4. Create translation fallback logic for content
5. Add RTL support for Arabic

### Phase 4: Testing & Refinement (Week 6)
1. End-to-end testing in all locales
2. RTL testing for Arabic
3. Performance optimization (bundle size, caching)
4. Translation quality review
5. Documentation updates

### Phase 5: Professional Translation (Week 7-8)
1. Integrate with translation platform (Crowdin/Lokalise)
2. Professional translation of Priority 1 languages (fr, es, ar)
3. Community translation setup
4. Translation memory setup

## Quick Reference: Session-Based vs URL-Based

### What Changes with Session-Based Approach

**✅ What DOESN'T Change:**
- URL structure (`/courses`, `/auth/signin` - all stay the same)
- API endpoint URLs (`/api/v1/courses` - unchanged)
- Route files location (no need to move files around)
- Link components (no locale parameter needed)

**⚙️ What Changes:**
- Root `layout.tsx` wraps children with `NextIntlClientProvider`
- Locale detected from session/cookie instead of URL
- `X-Locale` header sent with API requests
- Locale switcher updates cookie or database, then refreshes

**🔑 Key Implementation Points:**

1. **Frontend locale storage:** Cookie (`NEXT_LOCALE`) or DB (`preferred_locale`)
2. **Backend locale detection:** `X-Locale` header from frontend
3. **No middleware routing:** Just cookie management (optional)
4. **Locale switching:** Update preference → `router.refresh()` → UI reloads

### Quick Start Implementation Steps

**Step 1: Install & Configure (Day 1)**
```bash
cd apps/web
pnpm add next-intl
```

**Step 2: Database Migration (Day 1)**
```bash
cd apps/api
alembic revision --autogenerate -m "Add preferred_locale to users"
alembic upgrade head
```

**Step 3: Update Layout (Day 2)**
- Modify `apps/web/app/layout.tsx` to wrap with `NextIntlClientProvider`
- Create locale detection function (session → cookie → browser)

**Step 4: Create Translation Files (Day 2-3)**
- Create `apps/web/messages/en.json` with base strings
- Copy structure for `fr.json`, `es.json`, `ar.json`

**Step 5: Build Locale Switcher (Day 3-4)**
- Create dropdown component
- Save to cookie for guests, DB for authenticated users
- Call `router.refresh()` to reload UI

**Step 6: Add API Locale Header (Day 4-5)**
- Create `fetchWithLocale()` utility
- Update service layer to use it
- Backend detects from `X-Locale` header

**Total setup time: ~1 week** 🎉

## Summary: Why Session-Based i18n is Perfect for LearnHouse

### ✅ Technical Benefits
- **No routing refactor**: Existing `app/` directory structure stays intact
- **Cleaner URLs**: `/courses` vs `/en/courses`, `/fr/courses`
- **Simpler codebase**: Fewer files to manage, less complexity
- **Better performance**: No route duplication, smaller bundle overhead
- **Easier testing**: Test one URL pattern, not multiple locales

### ✅ User Experience Benefits
- **Persistent preferences**: Locale saved to database, survives sessions
- **Faster switching**: Change language without URL navigation
- **Cleaner sharing**: Share `/courses` instead of `/en/courses`
- **Better for SaaS**: Most users are authenticated anyway

### ✅ Implementation Benefits
- **Faster setup**: ~8 weeks vs 10-12 weeks (20-30% time savings)
- **Less code churn**: No need to refactor entire routing structure
- **Easier migration**: Update layout, add translations, done
- **Lower risk**: Fewer moving parts, less chance of breaking changes

### 📊 Comparison Table

| Feature | Session-Based (✅ Chosen) | URL-Based (❌ Alternative) |
|---------|---------------------------|----------------------------|
| **Setup Time** | 1 week | 2-3 weeks |
| **Routing Refactor** | None | Move all routes to `[locale]/` |
| **URL Changes** | None | All URLs change |
| **Link Updates** | None | Update every `<Link>` |
| **SEO Impact** | Moderate | Better (but less relevant) |
| **Code Complexity** | Low | Higher |
| **Bundle Size** | Smaller | Larger (duplicate routes) |
| **User Preference** | Persists (DB/cookie) | URL-based (can be lost) |
| **Locale Switching** | Instant refresh | Navigate to new URL |
| **API Impact** | None | None |
